# Files allowed to use raw concurrency primitives, and which ones.
#
# Everything else must go through jaal's safe types: a task or scope instead
# of std::thread, guarded<T> instead of std::mutex, loop_bound<T> instead of
# thread_local. See maya/third_party/jaal/docs/concurrency.md §7, and
# jaal's tests/lint/banlist.cmake for the check itself.
#
# WHY THIS FILE EXISTS. jaal runs that check over its OWN tree, which says
# nothing about a consumer: agentty could spawn a bare thread beside the
# loop, park reducer state in a thread_local, or forge a Sink, and jaal
# would never notice. Pointing the same check at agentty is what closes it.
#
# Each entry names the primitives that file may use, so a file allowed
# std::mutex still cannot sneak in a .detach(). Adding a line is a
# deliberate act: it says someone checked by hand that the raw primitive IS
# the implementation of a safe thing, not a shortcut around one.
#
# WHAT THIS BUYS, HONESTLY. jaal grades its guarantees (concurrency.md §6):
# Level A is "the bug cannot be written", B is "a tool catches it", C is
# "convention". Everything on this list is Level B. A file here has been
# READ and judged correct; nothing stops the next edit to it from adding a
# second lock and an inversion. jaal's guarded<T> would make that Level A
# (a second lock cannot be named inside with()/read()), and agentty uses it
# in zero places — 44 files hold a raw std::mutex instead.
#
# That is a deliberate position, not an oversight: most of these locks guard
# a process-wide cache read from CLI paths that have no kernel in scope, and
# guarded<T> binds to one. But it means the list is a promise to keep
# checking, not a proof. Two things keep it honest:
#
#   tests/seam_stress_test.cpp   drives the process-wide seams (provider
#                                selection, tool catalog, capability
#                                registry) from many threads under TSan.
#   allowlist_tight_*            fails the build when an entry outlives the
#                                code that justified it.
#
# When a file here gains a SECOND mutex, that is the moment to reach for
# guarded<T> or an owner thread instead of extending the grant.
#
# Paths are relative to src/ (the check runs once per scanned root).

# ── Owned background workers ─────────────────────────────────────────────
# Three subsystems own a thread that outlives any one turn. They are NOT
# jaal tasks because they are not part of a turn: they start at init and run
# until teardown, while jaal's task/stream lifetimes are per-Cmd and
# per-subscription. Each registers its own join with util::teardown, so
# main() cannot forget one — that registration is the safety property here.
#
# settings_cache: the write-behind settings worker. The mutex guards the
# pending value; the thread is the single writer. This is what keeps a disk
# round-trip out of the input path (see its header). thread_local: a
# re-entrancy guard so the worker's own write doesn't invalidate the cache
# it just filled.
runtime/app/settings_cache.cpp: thread mutex thread_local
io/blob_gc.cpp: thread mutex atomic detach
util/modelsdev.cpp: thread mutex detach

# ── HTTP: the turn's cancel token, and the transport ─────────────────────
# A streaming turn is a Cmd::task holding an http::CancelToken, tripped from
# a reducer on Esc. jaal has no effect for "cancel that specific in-flight
# request from a later step" — its stop_token is the runtime's, and fires
# when work stops being subscribed — so this atomic is the app's own. The
# reasoning is written out on the Sendable opt-in in runtime/cmd.hpp.
io/http.cpp: thread mutex atomic thread_local detach const_cast
io/tls.cpp: mutex const_cast

# ── Persistence and credentials ──────────────────────────────────────────
# Not reducer code: these run on a worker a task already put them on, or on
# CLI paths with no loop at all.
# The AsyncWriter owns a background worker thread that batches JSONL appends;
# see persistence.cpp AsyncWriter. Joined at shutdown via the teardown registry.
io/persistence.cpp: mutex thread
# The cross-process critical section. The mutex IS the point: it closes the
# in-process half of the race that the file lock cannot (jaal's file_lock
# conformance check 13). See include/agentty/io/shared_file.hpp.
io/shared_file.cpp: mutex
io/auth.cpp: mutex atomic const_cast
io/keystore.cpp: const_cast
io/cred_crypt.cpp: const_cast
airgap/airgap.cpp: const_cast

# ── Tools ────────────────────────────────────────────────────────────────

# The subagent run registry. A subagent runs on a Cmd::task_isolated thread,
# which jaal DETACHES — see jaal's kernel/pool.hpp, which says isolated
# threads are "asked to stop but never waited for". So the app can return
# from main() while a subagent is still inside its provider stream, and that
# stream holds the provider objects by reference off main's stack.
#
# The fix mirrors Zed's `running_subagents`: each live run publishes a cancel
# flag + a done latch, teardown trips them all and waits a bounded moment.
# That wait is the point, and it cannot be expressed as a jaal task — the
# threads being waited on are ones jaal has already disowned. atomic for the
# two flags (read from the run's thread, written from teardown's),
# condition_variable so a clean exit costs no fixed sleep.
tool/subagent.cpp: mutex thread_local atomic condition_variable
tool/commands.cpp: mutex
# Windows: run_command_s tees child output while polling for exit. It used to
# be a bare reader std::thread plus `std::mutex buf_mu` guarding four loose
# `shared_*` variables, joined ~90 lines later with a caller-supplied
# on_progress callback invoked in between — so a throwing callback meant
# ~thread on a joinable thread, i.e. std::terminate with no stack.
#
# Now jaal::scope() owns the reader (joined on EVERY exit path, so the [&]
# captures are warranted rather than lucky) and jaal::guarded<PipeBuf> owns
# the buffer with its mutex, so "took the lock" is not something to remember.
# jaal caught a real violation during the conversion: the first version
# passed `char*` into the lock body, which it rejects because a pointer
# argument is how a body reaches data the lock does not cover.
#
# Only `atomic` is left, for the reader_done flag the poll loop samples.
tool/util/subprocess.cpp: atomic
# Unique temp names for atomic writes, and a parallel directory walk.
tool/util/fs_helpers.cpp: mutex atomic
tool/util/sandbox.cpp: atomic

# ── Workspace scans ──────────────────────────────────────────────────
# The symbol index fans a directory walk across hardware_concurrency()
# workers and joins them before returning — a data-parallel scan inside one
# call, not a lifetime the loop has to track. It already runs on a jaal
# task; this is that task using its own thread.
workspace/symbols.cpp: thread atomic
workspace/files.cpp: mutex atomic
# checkpoint.cpp's atomic is a teardown cancel flag, and it is the one place
# here where the raw primitive is load-bearing rather than incidental.
#
# prewarm_repo_info() runs on jaal's ISOLATED pool. jaal waits for isolated
# tasks inside its shutdown grace, but only a task that RETURNS can be
# waited for — and this one's body is a pair of blocking `git rev-parse`
# spawns that force a function-local static. The flag is what lets it
# return early; Host::release() trips it before the pool's wait begins.
#
# Without it the spawns outran main(), and the CRT destroyed the static
# they were filling: intermittent abort on Linux, 0xC0000005 on Windows.
# A mutex would be wrong (teardown must not block on a subprocess spawn)
# and there is no kernel in scope for guarded<T>.
workspace/checkpoint.cpp: mutex atomic

# The exec capability's session drain. A process that outlives the call which
# started it has to have its pipe read by SOMEONE, or it fills at 64 KiB and
# the child blocks -- and polls are seconds apart by nature, so draining only
# inside poll() would stall exactly the chatty servers process_start exists
# for. This thread IS the implementation of mcp-cpp's Session capability,
# which is what lets that library own no concurrency at all.
#
# `thread` only: the shared state went to jaal::guarded<Shared>, the first use
# of it in agentty. So the lock cannot be forgotten, nothing escapes it, and
# a second lock cannot be named inside it -- Level A for the state, Level B
# for the thread. When tool execution becomes a keyed Sub::stream the thread
# goes too, and this line with it.
tool/util/exec.cpp: thread
# next_tool_exec_seq(): a static atomic counter minted per dispatch, echoed by
# the worker so the reducer can drop stale results from a superseded turn.
runtime/app/cmd_factory.cpp: atomic
# ACP dispatch fans a tool call out to std::async so a permission-request
# round-trip can happen alongside; the shared_future is awaited before return.
acp/server.cpp: async
# The Windows code-block runner ticks a heartbeat title/line while a blocking
# subprocess call runs. The helper is a jaal::scope() nursery spawn now, not a
# bare std::thread with an unguarded join (same std::terminate-on-throw bug as
# subprocess.cpp above), and it takes its own stop_token so Esc stops the

runtime/app/update/code_blocks.cpp: atomic

# View-layer render caches: NO LONGER LISTED, and that is the interesting
# part. They were four thread_locals (three LRU caches in agent_timeline.cpp,
# the render-phase flag in tool_body_preview.cpp) whose grant read "every one
# is a bounded LRU on the UI thread, documented at the definition;
# thread_local is how they say 'one thread owns this' without a lock."
#
# That is exactly the claim jaal's loop_bound<T> exists to CHECK rather than
# assert, and the failure mode it names is this one: a worker reaching a
# render cache does not crash, it silently gets its own empty copy and paints
# from it. A missing panel with no trace of why is worse than an abort.
#
# They are jaal::kernel::loop_bound<T> now. Reaching the value needs proof of
# being on the kernel's loop thread, the kernel arms that identity for its
# whole lifetime (so view(), which runs between steps, is covered), and off
# the loop the access aborts naming the rule. The on-loop path is unchanged:
# still no lock, still one thread.
#
# Dropping these two lines is the point of the exercise. An allowlist entry
# removed because the primitive was replaced by a checked one is the only kind
# of progress this file can record.

# ── i18n: the catalog pointer IS the live-switch mechanism ───────────────
# Not a shortcut around guarded<T>. guarded<T> would be the wrong tool here
# and would make the feature measurably worse.
#
# t() returns a string_view INTO the active catalog and is called a few
# hundred times per frame. guarded<T>::with() hands its state to a
# captureless lambda under a lock, so it cannot return a view that outlives
# the call -- the render path would have to copy every translated string,
# against 19 ns and zero allocation today.
#
# What the atomic actually does is LATE BINDING, the same shape colours use
# (docs/LATE_BINDING.md). A catalog is immutable once built, so there is no
# mutable shared state to protect: switching language is one release store
# of a shared_ptr and readers take an acquire load. The outgoing catalog
# stays alive through the shared_ptr until its last reader drops it, which
# is what makes a view handed out mid-frame safe even if the language
# changes during that frame.
#
# No lock is taken, so this file cannot participate in an inversion. Read
# and judged by hand, per the note at the top.
i18n/i18n.cpp: atomic
