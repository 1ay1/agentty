# Internationalization

Status: **design**. Nothing here ships until the core lands and the first
non-English locale is proof-read by someone who speaks it.

Twenty languages, listed at the bottom. This document is about the four
decisions that make or break a TUI translation, because the plumbing is the
easy part and getting these wrong is not recoverable once strings are out
with translators.

---

## 1. What this is NOT

**Not gettext.** `.po`/`.mo` is the obvious answer and it is wrong here for
three reasons: it needs a runtime dependency on libintl (agentty ships a
single static binary, including on musl and Termux), its plural syntax is a C
expression evaluated at runtime (an injection surface in a file we load from
disk), and `msgid`-as-English means every English copy-edit silently
invalidates every translation. We key on **ids**, not on source text.

**Not machine translation of the whole corpus.** ~5000 string literals exist
in the tree; the overwhelming majority are log messages, tool descriptions,
error detail for the MODEL, and internal identifiers. Translating those is
worse than useless — a model reading `sandbox: active (claybin)` in Hungarian
is a model that cannot act on it. See §3 for the line.

**Not a per-string `_()` sweep.** Wrapping every literal is how a codebase
ends up with 5000 translatable strings of which 400 matter. The catalog is
curated by hand and the lint keeps it honest.

---

## 2. The hard part is layout, not translation

A TUI has a fixed column grid. Three facts about that:

**CJK is double-width.** `你好` is 2 codepoints and 4 columns. maya already
gets this right — verified against `string_width`:

| input | script | columns |
|-------|--------|---------|
| `hello` | ASCII | 5 |
| `你好` | CJK | 4 |
| `こん` | Hiragana | 4 |
| `한국` | Hangul | 4 |
| `при` | Cyrillic | 3 |
| `éè` | Latin-1 | 2 |
| `🚀` | Emoji | 2 |

This is the single biggest reason this feature is feasible at all. Every
width decision in the renderer already flows through `string_width`, so a
Japanese label wraps and truncates correctly with **no layout changes**.

**German and Russian run long.** Measured on real agentty labels, translated
for this document and run through `string_width`:

| English | w | German | w | ratio | Chinese | w |
|---|---|---|---|---|---|---|
| `Also readable` | 13 | `Auch lesbar` | 11 | 0.85× | `也可读` | 6 |
| `Syscall filter` | 14 | `Systemaufruf-Filter` | 19 | 1.36× | `系统调用过滤` | 12 |
| `Secret scan depth` | 17 | `Tiefe der Geheimnissuche` | 24 | 1.41× | `密钥扫描深度` | 12 |
| `Applies on restart` | 18 | `Wird beim Neustart angewendet` | 29 | **1.61×** | `重启后生效` | 10 |

So the rule of thumb (+30-40%) understates the tail: a short English label
can nearly double. The worst case is not the average case, and a layout that
only survives the average is a layout that breaks on exactly the strings
users read most. The settings panes are the pressure point — two columns
(label + value) inside a hard frame.

The answer is NOT to shorten the German. It is to make the catalog carry a
**width budget** per string and fail the lint when a translation exceeds it,
so the problem surfaces at build time rather than as a clipped label on
somebody's screen. `width_hint` in the schema below.

**Some scripts need shaping we do not do.** Arabic, Hebrew, Devanagari,
Thai need bidi or complex shaping that a cell-grid TUI cannot do correctly.
None of the twenty target languages need it — that is not an accident, it is
why the list stops where it does. Adding `ar` or `he` later is a real project,
not another JSON file, and the catalog schema says so.

## 3. What gets translated, and what must not

The line is **who reads it**.

| audience | example | translated |
|---|---|---|
| the user, in the UI | `Also readable`, `applies on restart` | **yes** |
| the user, in a toast/status | `context compacted` | **yes** |
| the MODEL, in a tool result | `[sandbox] This command ran inside…` | **no** |
| the model, in the system prompt | the whole prompt | **no** |
| a log line | `openai.window_probe.model_info` | **no** |
| a settings key / id | `kSbReadPaths`, `"max_procs"` | **no** |
| a provider/model name | `Opus 5`, `claybin` | **no** |

The third row is the one people get wrong. agentty's sandbox denial note is
*deliberately* phrased for the model ("Do NOT retry the same command
unchanged") and exists to change its behaviour. Translating it degrades every
non-English user's agent, because the model's instruction-following is
strongest in English and the note's whole job is to be obeyed. Same for tool
descriptions: those are part of the API contract with the provider.

**Rule: if it crosses the wire, it stays English.** The lint enforces this by
rejecting `t()` inside `src/provider/`, `src/tool/`, and any function that
builds a request body.

## 4. Plurals are not a formatting problem

English has 2 forms. The target set needs up to 4:

```
en, de, nl, sv, da, no, it, es, pt-BR, hu, tr, id    1-2 forms
fr                                                    2 (0 is singular)
cs                                                    3 (1 / 2-4 / 5+)
pl, ru, uk                                            3 (complex)
zh-CN, ja, ko                                         1 (no plural)
```

Russian `5 файлов` vs `2 файла` vs `1 файл` is not a suffix rule, and
`"%d file(s)"` is not an acceptable answer in a product that claims twenty
languages.

So the catalog stores **CLDR plural categories** (`one`, `few`, `many`,
`other`) and the runtime picks one with a small hand-written selector per
language family. No expression evaluation, no runtime-parsed rules — a
`switch` on the language tag, which is 60 lines total for the whole set and
is testable exhaustively.

```json
"turns.count": {
  "one":   "{n} turn",
  "other": "{n} turns"
}
```

```json
"turns.count": {
  "one":   "{n} ход",
  "few":   "{n} хода",
  "many":  "{n} ходов",
  "other": "{n} хода"
}
```

A language that omits a category it needs fails the lint. A language that
supplies one it does not have (Japanese `few`) fails too — that is a
translator misunderstanding the schema, and it is better to catch it than to
silently never use the string.

## 5. Shape

```
share/i18n/
  en.json          the SOURCE catalog — hand-edited, reviewed like code
  zh-CN.json
  de.json
  …
```

Embedded in the binary via the existing resource mechanism (agentty ships as
one static file; a missing translation directory must not be possible). Hot
reload from `$AGENTTY_HOME/i18n/` in debug builds only, so a translator can
iterate without a rebuild.

### Catalog schema

```json
{
  "_meta": {
    "lang": "de",
    "plurals": ["one", "other"],
    "complete": 0.94,
    "reviewed_by": "…"
  },
  "sandbox.row.read_paths.label": {
    "text": "Auch lesbar",
    "width_hint": 18
  },
  "turn.count": {
    "one": "{n} Durchlauf",
    "other": "{n} Durchläufe"
  }
}
```

`width_hint` is the English width. The lint fails when a translation exceeds
it by more than a per-area allowance (panes are tight, toasts are not).

### Runtime

```cpp
// The ONE lookup. Missing id -> the id itself, visibly wrong rather than
// blank, and the lint makes it unreachable in a shipped build.
std::string_view t(std::string_view id);

// Plural form. `n` picks the CLDR category for the active language.
std::string tn(std::string_view id, long long n);

// Interpolation. Named placeholders only -- positional args reorder across
// languages and a translator cannot be expected to count.
std::string tf(std::string_view id, std::span<const Arg> args);
```

`t()` returns `string_view` into the loaded catalog, which is immutable for
the process lifetime — no allocation on the render path, which matters because
these are called per-frame.

### Language selection

1. `--lang` flag (one run)
2. `settings.json` `ui.lang` (the picker writes this)
3. `$LC_ALL` / `$LC_MESSAGES` / `$LANG`, first match wins
4. `en`

Region fallback: `pt-PT` → `pt-BR` → `en`. `zh-TW` → `zh-CN` → `en` is
**wrong** (Traditional ≠ Simplified) and is deliberately not done — `zh-TW`
falls straight to `en` until someone contributes it.

---

## 6. Why this cannot rot

Three gates, all in CI:

1. **Every id in the source exists in `en.json`.** A `t("foo.bar")` with no
   entry fails the build, not the render.
2. **Every id in `en.json` is used.** Dead strings are translator time spent
   on nothing.
3. **No `t()` in model-facing code.** §3's rule, mechanically enforced.

Plus a render test per language that paints the settings panes at 80 columns
and asserts nothing overflows — the CJK/German width claim, checked rather
than assumed.

---

## 7. Staging

This lands in order, and each step is useful alone:

1. **Core + lint + `en.json`.** No behaviour change: English strings move
   from literals to catalog entries. This is the big mechanical diff and it is
   reviewable because the lint proves nothing was dropped.
2. **The width/overflow render gate**, before any translation exists. It must
   fail on a deliberately over-long string, or it is decoration.
3. **`de` and `zh-CN`** — the two extremes (longest and double-width). If the
   layout survives both, it survives the other eighteen.
4. **The remaining seventeen**, which is then purely a content problem.

The language picker ships in step 1 with one entry. That is not a placeholder:
it proves the selection, persistence and fallback paths work before any
translation can hide a bug in them.

### Section headers must stop upper-casing

maya upper-cases section headers, with an **ASCII-only** loop
(`panel.cpp`, `render_item`):

```cpp
for (auto& ch : caps)
    if (ch >= 'a' && ch <= 'z') ch = char(ch - 'a' + 'A');
```

That is accidentally safe and visibly wrong, which is the worst combination
because it will not crash and nobody will file it. Measured:

| input | output | verdict |
|---|---|---|
| `sandbox` | `SANDBOX` | correct |
| `сеть` (ru) | `сеть` | untouched — no caps at all |
| `系统` (zh) | `系统` | correct, CJK has no case |
| `ışletim` (tr) | `ışLETIM` | **mixed case** |
| `größe` (de) | `GRöße` | **mixed case** |

The safety is real: because the loop is ASCII-only it cannot commit the
classic Turkish bug of mapping `ı` → `I`. But Russian headers get no emphasis
while English ones do, and German/Turkish get a ransom note.

A *correct* locale-aware upper-case needs ICU — a dependency agentty does not
have and should not take for one visual flourish. So the fix is to **stop
upper-casing** when the active language is not English, and let the rule plus
the dim-bold styling carry the structure. Those already distinguish a header
from a row (see the comment above that loop); the caps are belt-and-braces.

Pinned by a test over all five scripts above.
